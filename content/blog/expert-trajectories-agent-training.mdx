## 真人标注 agent 轨迹现在具体有哪些问题？

在 2024 年下半年开始做 WebChain 的时候，我越来越觉得采集真人轨迹数据／专家轨迹数据用于 agent 训练这件事还是一件非常困难的事情。今天真人 Agent 长轨迹数据仍然有几个比较根本的问题。

## 1. 人类行为不等于一个好的 agent policy

人类完成任务的时候，会有大量对模型来说非常奇怪的行为。

比如鼠标在页面上来回移动、上下滚动几下、停顿几秒、误点以后返回、打开一个页面看一眼又关闭，可能在这个过程中有效的步数只有一两步，但是记录的插件记录下来了大量的动作，scroll、hover、click、back 等等，导致噪声非常严重。

## 2. 真人操作 GUI 是连续发生的，而 agent dataset 通常是离散的

2025 年上半年，我们又继续迭代了数据采集插件，可以把真人交互轨迹通过视频的形式存下来，然后在视频中把操作时对应时间戳的界面图片提取出来（有点像今年一些公司蒸馏员工的办法），但是也遇到了很多问题，包括时间戳选不准、鼠标无法隐藏等问题。

人在 t 时刻点击鼠标，决定这个动作的视觉状态可能来自 t − 200ms 的页面。点击以后页面可能马上发生 hover、loading、DOM mutation。

如果从录屏里按照 timestamp 截图，偏差几十毫秒，就可能得到完全不同的 state，那页面和点击的坐标数据就对不上了。

以及鼠标什么时候隐藏？如果不隐藏的话，模型有可能学到的是鼠标的位置，因为鼠标在哪里，那次点击的坐标基本就在那附近。

另外，很多 GUI 页面会设计按钮的 hover 效果，如果鼠标移动到按钮上，会出现对应的文字高亮、颜色变化、边框变化，甚至弹出 tooltip 或其他视觉反馈，这就会进一步造成数据泄漏：模型看到的并不是点击前原始的页面状态，而是一个已经被鼠标位置“提示过”的界面。

这决定了模型看到的 observation，到底是不是产生这个 action 时真实对应的 observation。Agent trajectory 对 alignment 的敏感程度非常高，导致数据有较大的噪声。

## 3. 对于尝试失败的时候如何回退，真人采集的轨迹里占比很少

登录失效怎么办、前一步执行失败以后怎么恢复？这些状态在真人采集中比例很低。

所以大量真人数据教会模型的是：**在正确轨道上继续往前走。**

真实 Agent 需要学习的还有：**掉出轨道以后怎么回来。**

这也是 SFT trajectory 数据长期存在的一个结构性问题。高价值的 Agent 轨迹数据还包括 **failure → diagnosis → recovery**。

## 4. 真实网站的数据价值最高，同时也是最难规模化的

真实 Web 数据非常有价值，因为它包含 sandbox 很难复制的东西：

动态内容、真实商品、真实搜索、广告、cookie、账号体系、验证码、登录状态、推荐系统，以及真实世界不断变化的页面。

同时这些因素也直接限制了规模化采集。Anti-bot、rate limit、账号风险、隐私数据、支付流程都会出现。

而且今天采集的 trajectory，半年之后可能已经无法 replay。所以 Agent 数据还多了一个 environment decay 的问题。训练数据本身没有变，产生这条数据的世界已经变了。

这意味着高质量 Agent dataset 需要同时维护：**data + environment + verifier + replay mechanism**。数据集应该是一个完整的 infrastructure。

这在 Web 端真实网站上尤其困难，所以大家会选择 mock 网站、复制环境、合成环境、合成任务。（这就要引出我在做完 WebChain 之后，ICLR 的一篇工作 WebFactory 了，如何合成环境、合成数据，这是下一个小红书文章想讲的。）

## 5. 真人数据仍然很有价值，但采集流程确实不够成熟

怎样记录、怎样对齐、怎样清洗、怎样收集 reasoning、怎样采集 failure、怎样构造 reward，以及最后怎样把这些 trajectory 真正转化成 policy improvement，都还不成熟。

尤其对于真人交互的 trajectory，目前我觉得距离像文本数据一样直接用于大规模模型训练，还有相当大的距离。

所以目前大家能用上的数据，可能暂时还不是完整的专家轨迹，而是专家写下来的 rubric，以及专家在这个领域长期积累的 know-how——包括程序性知识和隐性的实操经验：专家脑子里“怎么做、怎么判断、遇到异常怎么处理”的方法，以及那些很难被完整写进手册的直觉、取舍、边界判断和踩坑经验之类的。
